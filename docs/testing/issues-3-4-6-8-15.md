## CI 39233232949: streaming assertion synchronization

[Linux job 117996017007](https://github.com/yeyuProject/pi-desktop-gui/actions/runs/39233232949/job/117996017007) failed at `test-polish-ui.mjs:239` on `d3b8397f`. The test's publish helper awaited `webContents.send` returning in the main process. That is not acknowledgment of React committing the renderer update. Its next `count === 2` assertion was true both before and after the append, so it provided no synchronization.

A single instrumented local run, with Chrome DevTools CPU throttling set to 8 only for the append, reproduced the same immediate assertion failure. Main-process sends, renderer receives and DOM mutations were recorded without filtering or changing runtime events:

The send trace has no production event between the two fixture publications or after the append. Production bootstrap patches earlier in the trace have no session ID and cannot replace this session in useRuntime. This rules out real-runtime overwriting in the reproduced failure. The original CI did not capture per-event timing; the trace proves the failing schedule locally rather than inventing missing CI telemetry.

The final change is five test-only lines: await the exact expected last thinking text with Playwright's existing bounded timeout, then retain both original count/content assertions. There is no sleep, timeout increase, retry, event suppression or product change. A slow positive control passes the complete polish suite at 8x CPU throttling. Two transport fault controls deliberately drop the append or replace it with CORRUPT_UPDATE; both fail at the semantic condition with TimeoutError. They use a shorter 1-second diagnostic timeout, while the committed test keeps its existing 15-second bound.
